# Changelog

Every tag both consumers pin. A release that changes a result on either side
says so here; everything else is a move.

## v0.14.0 — The Z report by person (2026-10-30)

**What changes:** nothing on a till or the server until a sale carries a picked person. A till
where nobody was picked at checkout folds to exactly the figures it did before
(`by_person` is empty, and the server omits it).

- `madar-till::report`: `Sale` gains `sold_by` (who was picked as serving at checkout,
  `orders.sold_by`) and `teller` (who was signed in, `orders.teller_id`). `Figures` gains
  `by_person: Vec<PersonLine>`: the till's SOLD sales (not voided, not refunded) by the picked
  person, else whoever was signed in, each with its order count, tenders (the payment
  summary's figure) and tips, largest first. The lines add up to `total_payments` and
  `total_tips`; the drawer is shared and is not split. Empty unless some sale on the till has a
  `sold_by`. `report::by_person` is the same function on its own.
- The vector check reads `sold_by` / `teller_id` from the order rows and treats a missing
  `by_person` as empty (the server omits it then).
- Vectors (regenerated by MadarRust): every `order` row carries `sold_by` / `sold_by_name`
  (null where nobody was picked), and `till_report_vectors.json` gains
  `picked_people_by_person` — two picked people, an unpicked sale, a voided and a refunded
  picked sale — whose `expected` has `by_person`.

**What changes:** nothing on a till or the server until they adopt the new functions. Every

  MadarRust `loyalty::gifts` and madar-core's `gift_eligible`. Pinned by the hand-written
  `loyalty_gift_vectors.json`.
- Like v0.7.x, the tag does not bump the workspace `version` (the crates' path dependencies

## v0.12.0 — Rewards dashboard: the card as data, stamp tracks (2026-10-23)

**What changes:** nothing on a till or the server until they adopt the new functions. Every
existing function and vector case is unchanged; the `public` and `full` browser packages are
byte-identical in behaviour (no export added or removed).

- `madar-card` (new): the Rewards card as data (REWARDS_DASHBOARD_DESIGN.md). `tracks` — a card
  holds 1–4 stamp tracks; track 1 is the programme's own card; tracks 2–4 have a size, a name,
  a stamp, a colour and a list of menu items (a POS sale earns on them with the one "Add points"
  press, a stamp per unit or per sale; completing the track covers one unit of any of them), or
  no items (a counter-only track); `validate_tracks`, `track_card`, `can_complete`,
  `stamps_within_cap`. `design` + `grid` + `templates` + `validate` — the card-design schema
  (v1) on a 12×6 grid, the ready-made templates (the default is today's look) and the checks
  that keep a design renderable. `render` — where elements land on Apple's strip and Google's
  hero and the strip as SVG (the server rasterises it; the dashboard shows it). `text` — the
  passes' stepper and `stamp_unit` (points | order | item | stamp, the unit every card prints). `audience` — who a dashboard message goes to. `message` — what it may say
  and the send limits. Pinned by `card_design_vectors.json` and `card_rules_vectors.json`.
- `madar-loyalty::tracks` (new): `plan_tracks`, the redemption planner across a card's tracks
  (one reward per line, each track its own balance, one shared per-order cap; strict on the
  server, trimming on the till), `tracks_for_line` (the till's chooser), `track_programme`.
  A sale on track 1 alone is `plan` itself: every `loyalty_plan_vectors.json` case answers the
  same through it. Pinned by `loyalty_tracks_vectors.json` (hand-written).
- Capabilities `loyalty.card.design` (254) and `loyalty.broadcast` (255), owner and manager by
  default, behind the `loyalty` feature; no legacy cell.
- `madar-web`: a fourth, lazily loaded package `card` (`madar_card.js`): `card_rules`,
  `card_templates`, `card_default`, `card_validate`, `card_first_free`, `card_layout`,
  `card_svg`, `tracks_validate`, `track_card`, `card_stepper`, `card_stamp_unit`, `audience_validate`,
  `message_validate`, `message_line_for`. CI attaches `madar-web-card.tar.gz`.
- Like v0.7.x, the tag does not bump the workspace `version`. v0.11.1 (`send_cart_to_kitchen`,
  branch `feat/kitchen-cart-send`) is NOT in this tag: it was never merged to main.

## v0.10.0 — madar-menu: the self-serve menu import (2026-10-18)

**What changes:** nothing on a till or the server yet. A new crate; every existing function and
vector file is byte-identical, and the `public` browser package is byte-identical too.

- `madar-menu`: `BulkMenu` (the JSON a dashboard sends to `POST /menu/bulk`) and `validate`, the
  server's checks before it writes one; `foodics::parse` (feature `foodics`, the `csv` crate) reads
  a Foodics console export into a `BulkMenu` plus row warnings. Sizes come from a group with
  reference `size`, or from a group named like sizes that is pick-exactly-one with size-like
  options; one that fails the test stays a group with a `looks_like_sizes` warning.
  A milk/beans (swap) group is one pick at most (the dashboard's rule): `validate` refuses
  otherwise (`swap_not_single`), the reader reads a pick-many one as extras (`not_a_swap`). An
  item with sizes needs one on sale (`no_active_size`).
- `utoipa` feature (off by default): `ToSchema` on the bulk types, for the backend's OpenAPI.
- `confirm`: `replace_sentence` (EN/AR, shown by the dashboards) and `confirms_replace` (the
  server's check of the typed sentence, either language, compared like names).
- `madar-web` `menu`: a third browser package (`madar_menu.js`, 58 KB brotli) with `foodics_parse`,
  `bulk_validate`, `replace_sentence`, `confirms_replace`, for the dashboard to load when its import
  dialog opens. `public` and `full` carry none of it (`full` stays the size it was).
- `vectors/menu_import_vectors.json`: reader, check and sentence cases, run natively and through the
  `menu` package.

## v0.8.0 — the Free plan, defined once (2026-10-13)

**What changes on a till or the server: nothing yet.** A new crate and a new spec file; every
existing function and vector file is byte-identical. Nobody has a plan until a consumer reads one
(every organisation is Paid), and `topics_for_role` still lives in madar-core until its swap.
Like v0.7.x, the tag does not bump the workspace `version`.

- **madar-plan** (new; FREEMIUM_SPEC_2026-10-11.md §3): `Plan { Free, Paid }` (serde `"free"` /
  `"paid"`; anything else, `null` included, reads as Paid, so an old server never locks a paying
  shop out); `entitlements(plan)` → `Entitlements { features, limits, realtime }`; `ceiling(plan)` and
  `apply(plan, EffectiveSet)` (intersection with the plan's capabilities; limits and "ask a manager"
  fall with their capability; core capabilities always survive); `may_add_branch(plan, live)`,
  `may_activate(plan, DeviceKind, DeviceCounts)`; `downgrade_keeps(tills, picks)` (the owner's pick
  per branch, else the most recently used till, a never-used one last, ties to the smaller device
  id); `realtime_topics(plan, role)` and `Topic`; `Refusal { code, feature }` with `en()`, `ar()` and
  `message(locale)`. Codes: `plan_feature`, `plan_branch_limit`, `plan_device_limit`,
  `plan_no_realtime`, `plan_till_inactive`. A kind of device limited to zero (kitchen screens,
  waiter devices) refuses as the feature it needs ("Kitchen screens are on the paid plan.").
- **`realtime_topics` is madar-core's `realtime::topics_for_role`, moved.** Paid answers exactly
  what it answered (`kitchen`: kitchen, sync; `waiter`: tickets, kitchen, floor, bookings, sync;
  every other role: delivery, kitchen, tickets, orders, floor, bookings, tills, sync), as `Topic`s
  instead of strings. Free answers nothing: its tills open no stream. `Topic` is the backend's
  `realtime::event::Topic`, with the same wire names.
- **`authz/spec/plans.toml`** (new): nine features (`inventory`, `loyalty`, `online`, `bookings`,
  `floor`, `kitchen`, `dawam`, `branding`, `basira`), each a set of capability groups and
  key patterns, and the plans: Free has no feature, one branch, one POS device per branch, no kitchen
  screens or waiter devices, no realtime; Paid has all of them, unlimited. `branding` and `basira`
  gate no capability (nothing in the registry names them); the apps and the server check the feature.
- **authz-gen** validates `plans.toml` against `capabilities.toml` (every group and capability
  exists; no core capability behind a feature; a capability behind at most one; every non-core
  capability behind a feature or listed free, so a new capability never silently joins Free; Free
  never looser than Paid) and writes `crates/madar-plan/src/generated.rs`,
  `<dashboard>/src/generated/plans.ts` (`--dashboard`) and
  `<pos>/packages/app_core/lib/src/generated/plans.dart` (`--pos`). `--check` covers the Rust file.
- **madar-web `public` and `full`**: `entitlements(plan)` (the plan as a string; unknown is Paid),
  run through the wasm against `plan_vectors.json`.
- **`plan_vectors.json`**: both plans' entitlements, spot checks of the ceiling, the ceiling over
  every template's role grants (restaurant and café, each role, both plans), every limit at and past
  its boundary (a downgraded organisation's two branches included), the downgrade's picks, topics per
  plan and role, and the refusals' exact wording in both languages.

## v0.7.2 — the menu's order, one rule for the till, the public menu and the store (2026-10-13)

**What changes on a till: nothing** (the POS core's category sort moves here; its order is the
same except that two categories with the same position and the same name now order by id instead
of by whatever order they arrived in). **On the server and the customer pages:** the public menu
followed none of it (MadarRust `load_public_menu` listed categories `ORDER BY name`), so a shop
that dragged Coffee above Breakfast on the dashboard saw that on the till and the reverse on its
QR menu and online store. They now run this rule.

- **madar-catalog `order`** (new): the POS's rule (madar-core `menu::categories`) — categories by
  `display_order` (missing or `null` is 0), then the name the reader sees, compared by Unicode
  code point (Rust `str` order: not a locale collation, and not JavaScript's UTF-16 order), then
  `id`. `cmp` / `sort` over keys a reader already resolved (the POS core's views),
  `category_order(&[Category], locale)` over the API's categories (the indices in order), and
  `resolve_name` — madar-core's `menu::resolve` moved here unchanged (the exact locale, its
  language, `en`, the base name; an empty or non-text translation is none). `Translations`, the
  API's `name_translations` without a JSON value (non-text entries dropped). Hand-computed
  `menu_order_vectors.json`: 8 resolve cases, 13 order cases (ties, missing and `null` positions,
  a negative one, the same categories read in English and in Arabic, an untranslated name among
  Arabic ones, code points vs a collation and vs UTF-16, equal names, names equal only in Arabic).
  Menu items have no order of their own (`menu_items.display_order` was dropped in 2026-06):
  every reader shows them as the server lists them.
- **madar-web `public` and `full`**: `category_order(categories, locale)` → the indices in order
  (`OrderCategory` in the `.d.ts`; other fields of the API's categories are ignored), run through
  the wasm against `menu_order_vectors.json`. Brotli, wasm + glue: `public` 76 → 82 KB, `full`
  165 → 171 KB.

## v0.3.0 — C, catalogue pricing (2026-09-24)

New crate `madar-catalog`: how a sale line is priced from the catalogue.

- The rule is the SERVER's, moved from MadarRust `orders/handlers.rs`
  (`catalog_unit_price`) and `orders/component_resolve.rs` (`swap_target`,
  `collapse_families`, `merge_sized_option_lines`, the pricing half of the
  resolver) with its two swap-family tests. The server's results did not
  change: every case of `catalog_vectors.json` (54 lines over 7 items and
  20 options) was checked against the order path's answers taken before the
  move, stock deductions included.
- `view`: `CatalogView` — an item (sizes with their branch prices, the
  branch's item price, the recipe's lines per size and its default size, the
  swap bases' candidates, the optional fields) and the options (price, type,
  group, effect, swap category, the ingredient it replaces, its lines per
  size). The backend builds it from SQL; `feed` rebuilds it from the
  `pricing` the backend now ships on every `/menu-items?full=true` row and
  every add-on row.
- `price`: `price_line`, `price_options` (a bundle component), `unit_price`,
  `option_charge` / `is_recipe_choice` (what a sheet shows and preselects),
  `swap_target`, `collapse_families`, `merge_sized_lines`.

**What changes on a till built against v0.3.0** (the server's answer, where
the till's own swap families and size rule disagreed; a tablet in the field
keeps its old pricing until it updates, and the server flags — never
refuses — a sale priced the old way):

- An explicit `swaps` group (a tea group over a black-tea recipe): green is
  charged the 400 difference, not 700; the recipe's black is free, not 300.
- An option sharing the recipe's ingredient with the default (a "barista
  whole" at 300 beside whole milk at 0) is the recipe's own choice: 0, not 300.
- A swap is charged over the recipe's option in the chosen option's own group
  first, the active ones before an inactive one (not over
  `default_milk_addon_id`).
- A swap group picked twice keeps the LAST pick once, where it was picked
  (a till sent vanilla ×2 + caramel as additive: 650; now caramel ×1: 50).
- A line with no size is the branch's item price, else the lowest active
  size (was the lowest size); an inactive size or a size only the branch
  prices takes the server's fallback.
- An optional field offered on another size only is skipped.
- The recipe preview swaps what the rule swaps.
